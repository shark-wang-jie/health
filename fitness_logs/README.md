# 饮食、训练与体重记录

规则版本：2026-09-08 v3.2（数据schema仍为3）。适用于后续新日记录；已封账历史保留原值和原算法。用户明确更正优先。证据与适用边界见 [科学依据](reference/evidence.md)。

## 当前执行方案

[当前计划配置](current_plan.json)是新建日记录的配置来源，包含档案、目标和模型参数。计划调整时先将旧配置存入plans目录，再记录新版本、递增revision、生效日期和理由；CLI新建日根据日期选择已生效版本，新日复制配置快照，历史日不跟着改变。补记日期不套用未来计划。下列文字描述的是当前初始方案，不在每天创建时重新硬编码覆盖调整后的目标。


- 男，27岁，173厘米；最新空腹体重91.80公斤（09-08）。BMR按米夫林公式作参考，不作为最低摄入需要或饮食上限。生日未知，年龄不擅自推算。
- 初始摄入安排：休息日约1800千卡，训练日约1900–2000千卡。日均估算缺口参考400–600千卡，每周下降约0.3–0.6公斤；这些是当前个人执行目标，不是人人适用的处方，也不要求两套数值每天恰好同时满足。
- 初始模型 `tdee_v1`：BMR×1.2＋当次训练动态千卡×0.75。久坐假设、1.2和0.75均为待校准模型参数；保留原始训练消耗，不叠加全天活动圆环、不加总千卡。步数可以记录以解释活动变化，不再机械换算加到消耗中。
- 蛋白质170克保留为参考目标；当前实际安排可参考约140–180克/日，分散到3–4次进食，优先正餐中稳定供应。不为凑170克硬塞食物。运动人群一般证据范围约1.4–2.0克/公斤/日，不等于当前体重越高就必须无限加量。
- 碳水150–180克是旧计划参考，按训练、饥饿和总饮食灵活调整，不当作硬上限。正常保留膳食脂肪，不为增加蛋白质挤掉全部主食、蔬菜或脂肪。
- 饮食质量同时看蔬果、多样性、全谷豆类和纤维。WHO一般参考为蔬果至少400克/日、食物来源纤维至少25克/日；未报告不填造，微量营养或纤维缺失不当作零。总碳水不能直接写成糖。
- 保留力量训练并按恢复逐步进展。记录动作、重量、次数/组数、主观强度（用户提供时），比“燃烧了多少卡”更能反映力量训练进展；不能从心率、时长或热量推断负荷和训练质量。近期研究支持减脂时力量训练有助于保留去脂体重，即使秤上的减重未更多；不把体重下降速度作为唯一训练评价。不做断食或惩罚性运动补偿。

## 每次记录流程

1. 读取交接摘要、目标日JSON和有关食物口径；日期按Asia/Shanghai核对。睡醒不等于跨日，明确补报按指定日。
2. 新日期用 `python3 fitness_logs/record_tools.py new YYYY-MM-DD --weight 91.8`。未称重省略weight，BMR沿用最新有效体重并记录来源日期，空腹体重保持null；不建立未来实际日或覆盖已有日。
3. 只修改真实条目。`id`稳定且唯一；重复消息不新增，明确又吃一份才用新id；更正替换原条目并在`corrections`记录时间、原值、新值和依据。
4. 更新饮食完整性、训练状态、待确认项；重新计算 `python3 fitness_logs/record_tools.py recalculate 路径`。工具检查条目、公式和状态，运行jq后原子写入。
5. 独立检查用 `python3 fitness_logs/record_tools.py validate 路径`。语法正确不等于数值正确；工具还检查求和、BMR、余量、宏量范围、消耗来源和重复id。检查通过不无故重复。
6. 日报用`python3 fitness_logs/record_tools.py report 日文件路径`生成一致表述：基础/含余量摄入、基础蛋白质/脂肪/碳水及重要不确定项；资料完整时再列模型TDEE和按含余量摄入估算的缺口。开放日只称“截至目前”；`estimated_deficit_kcal`为兼容保留的模型消耗减已记录摄入，必须结合`energy_balance_scope`解释。日报最终缺口使用`completed_day_estimated_deficit_kcal`，未封账或关键资料不完整时为null，不把当前差额当成最终全天缺口。不以大缺口作为成功指标。

## 食物估算与口径

- 用户于2026-09-09明确选择简化记录：日常少量鱼油、纯肌酸、谷氨酰胺及普通维生素/矿物质补剂不计入摄入热量，也不计入宏量营养目标；这是用户选择的记账省略，不代表所有补剂实际零热量。当前未记录过这些补剂热量，不追溯新增或扣减历史总数。此约定不扩展到蛋白粉、增肌粉、含糖运动饮料等明显提供营养能量的食品；若以后剂量或产品明显改变，再说明其影响。肌酸的使用变化仍可记录以解释体重水分变化。

资料优先顺序：实际食用说明和本次清晰标签 → 已确认同款 → 匹配食物数据 → 照片和一般估算。没有秤也可以记录，只有会明显影响判断的歧义才简短澄清。

- 记录实际吃下部分：去皮、骨头、剩饭、没喝汤扣除；附着油、糖和酱汁适量计入。只算用户自己的食物。
- `kcal_base_estimate`为基础点估算，`kcal_booked`为记账值，`kcal_range`为合理估算范围。无标签餐食可在基础估算上留约10%余量，油多且未知可约10%–15%；不是科学校正，不机械取极端上限。
- 标签与食用量明确时两值相同；已有份量/用油余量时不再叠加。无油单一食物、已知个数或匹配规格可以主要用范围表达不确定性，不能把“所有食物统一加10%”作为规则。
- 额外油/酱汁记在`margin.added_fat_g`和`added_carbs_g`，原有宏量点估算已经包含这些新增假设；`base_macro_estimates`另存扣除明确附加余量的基础宏量。日报优先基础宏量，记账宏量只描述含余量的组成，不宣称实际多吃了相应油脂。蛋白质不随热量同比增加。总热量与4/4/9换算存在标签取整、纤维差异，不为强行相等篡改标签。
- 条目用`consumed`、`consumed_estimated`、`planned`、`not_eaten`；计划/没吃不计总量。确认吃了但重量不明用暂估状态及`uncertainty`，不能把金额擅自当克数。日常照片估算本身不等于记录缺失；会显著改变摄入结论的未决歧义放入`missing_sections`。无关能量的备注放入`non_energy_pending_notes`，不因此阻断校准；未知包装重量不能当作无关细节。
- [机器可读常用食物库](food_catalog.json)固定常吃同款的基础值和余量。可调用`food_from_catalog(food_id, entry_id, servings)`缩放，结果拷贝进当日日记录；目录更新不改变历史。标签类每100克条目仅在食用克数明确时直接使用，否则改为暂估来源和范围。
- [其他历史食物参考](reference/food_defaults.md)保留未结构化口径；首次使用时明确基础值、是否已有余量，然后再固定新版本。套餐变化说明鸡腿数量、饭量、卤蛋和用油差异。
- 食物范围不是统计置信区间，缺口也不是真实缺口下限。长期一致记账比虚假的个位数精度重要。

## 数据结构与状态

新日文件`schema_version: 3`，示例见 [模板](templates/daily_v3.json)。模板不是实际摄入记录。宏量只有点估算而无范围时保留未知范围，不制造零宽区间；月总结注明有范围的数据覆盖天数。

- `energy_method`明确`algorithm: tdee_v1`、`activity_factor: 1.2`、`training_factor: 0.75`；`food_estimation_policy: photo_margin_v1`。方法变更必须保存生效日期与理由；摄入口径变化的窗口不混合校准。活动系数变化须单列解释，不能因反推消耗而同时拟合BMR、运动误差和食物误差，现有数据无法分别辨识它们。
- `profile_snapshot`保留体重来源日期、身高、年龄、公式参数及BMR。`daily_summary`由同一计算逻辑生成，禁止在不同文件凭记忆手写总数。
- `training_status`区分`unknown`、`confirmed_rest`、`reported_training`。训练能量未知允许null并报告暂估，不用总千卡顶替动态消耗；`energy_scope`只能是`session_active`。另用`training_coverage`区分unknown/partial/confirmed_complete：有一段训练不代表全天训练报完。明确休息或用户确认当天训练全部结束可判完整，不需要重复问。
- 每次训练须有稳定`event_id`；同一次骑行若手表和单车都记录，选择一份当次动态消耗计入，其余读数嵌在同一条目作对照，不能相加。不同训练才新增事件。跨午夜训练保留实际起止时间，默认按开始日归属一次，若明确拆分须避免重计。训练动作细节和恢复信息按用户实际报告保存。
- `food_coverage`区分`unknown`、`partial`、`confirmed_complete`。未报告早餐不能写成没吃；确认当天记录结束不自动等于全部餐食已核实。
- `record_status`为open/final/partial；final须有`closure_basis`且`food_log_closed=true`。用户确认结束，或开始新一天且前一天无新增记录，可封账；`missing_sections`和条目不确定性继续保留，封账后允许明确补报更正。
- `recovery`可保存饥饿、睡眠小时、训练表现、疲劳或疼痛；未报告为null，不为记录强制每天问卷。
- 子成分可留在条目内作说明，计算只取顶层条目，不能又把子成分复制成独立食物重复计入。

## 趋势、校准与月总结

- `python3 fitness_logs/record_tools.py review --end YYYY-MM-DD`跨月读取最近28天；分成四个不重叠7日窗口，注明每窗称重次数，不插补。可加`--output 路径`保存只读分析结果。
- 摄入与体重反推平均消耗的粗校准要求28天连续、摄入估算同口径、封账且饮食资料完整、每窗至少4次称重，无影响摄入解释的未决项或明显体重干扰。训练热量不是此反推的必要输入；仅在比较训练消耗模型时才要求训练资料完整。这是内部质量门槛，不是医学标准；不满足时仍展示可用的体重趋势及数据缺项，不输出粗校准TDEE。只要有至少4次有效称重且覆盖至少7天，就可描述体重线性趋势，无须等待28天或手表数据；该展示门槛也是执行约定。
- 趋势按28天内全部有效空腹体重及实际日期作线性拟合，周均同时保留用于观察，不再只比较首尾两周。用于反推消耗的摄入区间为首次有效称重日起至末次有效称重日前一天，避免把最后一次称重后的进食算入此前体重变化。
- 多周粗估日均能量差可参考每周下降公斤×7700÷7；不能将水分、糖原或胃肠内容物变化当脂肪，也不是长期恒定能量模型。由偏高记账摄入推回的TDEE会吸收摄入偏差，只适合同口径安排。
- 结合连续多周趋势、饥饿、力量表现和恢复再调整；必要时每次约100–150千卡并继续观察，通常至少观察约两周趋势再讨论下一次调整，恢复不佳则及时处理，不自动执行，不随单日体重调整。明显持续疲劳、疼痛或不适优先处理恢复，不能为了等满28天而忽略。
- `python3 fitness_logs/build_monthly_summary.py YYYY-MM`仅在上海时间该月结束后生成，缺日或未全封账则标记未最终完成。未指定月份只会为已结束且没有总结的月份生成文件；已有总结默认跳过。明确重生成时使用`python3 fitness_logs/build_monthly_summary.py YYYY-MM --overwrite`，不允许省略月份批量覆盖。
- 尽量同一台秤、相近时间、起床排空后、进食饮水前和相近衣着称重，记录明显条件差异；不要求额外脱水或反复称重。与平常不同的读数保留说明，不为了趋势平滑而删除。
- 疾病、明显水肿、开始肌酸、药物变更或称重条件明显改变等已报告情况，记入`trend_context`，自动粗校准暂停并人工复核；普通高盐一餐只作解释，不自动当成脂肪增加，也不必每次阻断28天窗口。
- 月总结分别列出基础/偏高摄入、蛋白质/脂肪/碳水、训练原始/折算消耗、训练次数/时长、体重、资料覆盖及恢复报告。新旧缺口严格分开；新算法缺口合计仅含最终且关键资料完整的日，并列明参与天数，未完成日的暂算差额不累加。摄入与已知训练仍按已报告量汇总，跨估餐口径摄入合计只是记录值合计。
- 目标区间仅描述高于/处于/低于安排，不称为合格评分；资料不完整日不参与新口径目标比较。蛋白质只称按记录点估算或范围达到参考值，不称“确定达标”。
- 旧日JSON不自动迁移或重算；旧算法差额不代表真实盈余/缺口。历史月总结保留，明确要求重生成时才更新。

## 用户训练习惯

- 2026-09-12用户说明：周末一般为休息日。后续沟通沿用这一默认安排，周末当天结束且无训练或相反信息时，可按休息日结算并注明依据，不重复询问；实际补报训练优先。日内新建记录仍保留unknown，避免把日常安排预先写成已完成事实；不追改其他历史日。

## 训练记录的可选细节

只在用户提供时保存`exercise_entries[].resistance_sets`：动作`exercise_name`、器械`equipment`、重量口径`load_basis`（例如杠铃总重、单只哑铃或器械配重）、每组`load_kg`/`reps`、`set_type`（warmup/working）、可选`rir`。自重或负重未知用null，不能虚构体重负荷。

月总结排除热身组，只比较动作、器械和重量口径相同的工作组；不把器械标称重量当自由重量，也不由总吨位推断肌肉增长。不要求记录所有组，只有训练截图时保留原训练记录即可，不因为缺组数禁止复核饮食或体重。

## 交接

交接摘要只保留当前状态、有效规则入口、关键默认口径入口、待确认项。历史详单查对应JSON。每天22:00（亚洲/上海）保留更新交接的约定；用户在接近或超过22:00提出要求时更新。当前文件规则本身不是后台定时任务，不宣称已配置自动触发。

修改规则同步README、交接和相关模板/脚本。回归检查：`python3 -m unittest discover -s fitness_logs/tests -v`。
